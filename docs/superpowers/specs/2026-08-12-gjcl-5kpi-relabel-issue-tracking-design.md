# 5-KPI 라벨 리네이밍 + 제264회 실측 데이터 반영 + 이슈추적사항 탭 — 설계 스펙

> **상태**: 승인됨 · 2026-08-12
> **상위 문서**: `docs/rubric/CLAUDE.md` v2.1(본 스펙 반영 후 갱신)이 최상위 평가 루브릭. 본 문서는 그 루브릭을
> 실제 코드(채점 함수·DB·API·모바일 UI)에 반영하는 제품 설계 스펙이다.
> **선행 스펙**: `docs/superpowers/specs/2026-08-11-gjcl-5kpi-rubric-design.md`(v2.0, 8축→5-KPI 전환) —
> 그 문서는 수정하지 않고 동결된 이력으로 둔다. 본 문서는 v2.0 위에 쌓이는 후속 변경만 다룬다.

## 배경

배포된 모바일 앱은 `master`가 아니라 워크트리 `worktree-gjcl-5kpi-rubric`의 5-KPI 코드로 만들어졌다. 사용자가
실제 화면을 확인한 결과 근거밀도(KPI①)가 거의 모든 행에서 "―"로 나오는 것을 발견했다. 원인은 표시 로직이
아니라 `computeEvidenceDensity`가 "발언시간(초)"을 분모로 쓰는데, 스크래퍼가 이 값을 절대 수집하지 않아
`processStatement.ts`에서 항상 `null`로 고정되어 있었기 때문이다(`backend/lib/pipeline/processStatement.ts`
의 `speechDurationSec` TODO).

이 기회에 사용자는 5개 KPI의 한글 명칭을 더 명확한 이름으로 전면 교체하고, 그 중 2개(사전준비도·실시간
압박력)는 공식 자체도 구체화했다. 또한 제264회 임시회 회의록을 직접 검토해 얻은 실측 검증값을 화면에 실제로
노출하고, "전체의원랭킹" 탭을 완전히 다른 성격의 "이슈추적사항" 탭(의원이 제기했지만 아직 재검토되지 않은
사안 목록)으로 교체할 것을 요청했다.

## 범위

**포함**:
- 5개 KPI 한글 라벨 리네이밍(표시 문자열만 — 내부 식별자·DB 컬럼명은 불변)
- 사전준비도(구 근거밀도) 공식: 분모를 발언시간(초) → 발언 어절수로 교체
- 실시간압박력(구 추궁심도) 공식: 보너스 가산을 수치값에서 분리(태그로만 표시), 가산 태그 "회피차단"→"쟁점고정" 리네이밍
- 위 공식 변경의 기존 채점 데이터 소급 백필(순수 코드 재계산, AI 호출 없음)
- 제264회 임시회 실측 검증 데이터 DB 직접 시딩(7인 × 5-KPI + 이슈 티켓 8건)
- "전체의원랭킹" 탭 → "이슈추적사항" 탭 전면 교체(새 스키마 컬럼·API·컴포넌트)

**제외(비범위)**:
- master 브랜치 머지/동기화
- 5-KPI 내부 식별자·DB 컬럼명 리네이밍
- 264회 외 기존 발언의 근거밀도(사전준비도) 재처리 — 구 프롬프트로 추출된 인용에는 "정확성 검증" 규칙이
  없었으므로 새 공식을 적용해도 신뢰할 수 없어 N/A로 유지
- 영상/타임코드 기능(저장소 전역 금지 — 무관, 언급 안 함)

## 1. KPI 라벨 매핑

| 내부 식별자(불변) | 구 라벨 | 신 라벨 |
|---|---|---|
| `evidenceDensity` | 근거밀도 | **사전준비도** |
| `solutionSpecificity` | 대안구체성 | **정책생산력** |
| `interrogationDepth` | 추궁심도 | **실시간 압박력** |

## 2. 사전준비도 공식 변경

```
사전준비도 = (L법령조문 + S정량통계 + P검증가능선례 + F현장확인) 인용 수 ÷ 발언 어절수 × 100
```

- 분모가 "발언시간(초)"에서 "발언 어절수"로 바뀐다. 어절수는 `statements.rawText`에서 공백 분리로 즉시 계산
  가능하므로, 스크래퍼가 수집하지 않는 값에 의존하던 기존 문제가 근본적으로 해결된다.
- 등급 경계값(≥3.0=A, 2.0–2.9=B, 1.0–1.9=C, <1.0=D)은 불변.
- 의례적 인사말(감사 인사·소개)은 어절수에서 제외하는 것이 이상적이지만, 기계적 어절 분리로는 완벽히
  구별할 수 없다 — 알려진 근사로 문서화하고 별도 NLP 전처리는 하지 않는다.
- 신규 규칙: 인용의 정확성 검증 필수. 존재하지 않는 조문·오류 통계를 인용한 것으로 판명되면 해당 인용은
  분자에서 제외(−1건 처리). 이는 Sonnet5 추출 단계의 지침으로 루브릭 문서에만 기록하고, 별도 자동 검증
  코드는 만들지 않는다(§3④ 회피 판정 예시와 동일한 성격의 서술적 규칙).

## 3. 실시간압박력 공식 변경

```
추궁깊이 = 질의 1건당 평균 왕복 턴 수
재질의율 = 답변 후 재질의한 건수 ÷ 총 질의 건수
```

- 기존 코드는 `qaRounds.length + 가산점 합계`를 수치값으로 썼다. 신규 공식은 가산 태그를 수치에 합산하지
  않고 각 round에 태그로만 남긴다 — 왕복 턴 수 자체가 수치값이 된다.
- 가산 태그명 변경: 모순포착(+1.0)·패턴제시(+1.0)·**쟁점고정(+0.5, 구 회피차단)**·법근거제시(+0.5). 쟁점고정의
  새 정의: "상대의 화제 전환을 차단하고 원 쟁점 복귀".
- `재질의율`은 기존에 `qaRounds.length - 1`이라는 원시 카운트를 그대로 "비율"이라 부르던 버그였다. 신규
  정의로 `qaRounds.length > 1 ? 1 : 0`(해당 질의가 재질의로 이어졌는지 여부)로 고친다.
- 근거: 최양희 실측 사례 — 질의 1건, 왕복 4턴, 깊이=4.0(가산 미포함), 재질의율=100%.

## 4. 기존 채점 데이터 백필

3번 공식 변경은 264회 샘플만이 아니라 이미 채점된 모든 발언의 `kpiInterrogationDepth`/`kpiReQuestionRate`에
영향을 준다. 저장된 `qaRounds` jsonb만으로 순수 코드 재계산이 가능하므로(AI 재호출 불필요), 별도 백필
스크립트로 전체 재계산해 신·구 공식이 혼재하는 상태를 만들지 않는다. `kpiEvidenceDensity`(사전준비도)는
백필하지 않는다 — 인용 자체가 "정확성 검증" 지침이 없던 구 프롬프트로 추출됐기 때문에, 새 분모(어절수)를
적용해도 분자(인용 정확성)가 검증되지 않은 값이라 신뢰할 수 없다.

## 5. 이슈추적사항 탭

기존 "전체의원랭킹"(의원별 KPI 평균 순위표)을 완전히 다른 화면인 "이슈추적사항"(의원이 회의 중 제기했지만
아직 재검토되지 않은 사안의 정적 목록)으로 교체한다. 데이터 원천은 기존 `issueTickets` 테이블이지만,
"확인 시점"(예: "다음 정례회", "착공 후 첫 회기")을 담을 컬럼이 없어 `reviewCheckpoint: text` 컬럼을 추가한다
(nullable, drizzle migration). 티켓 번호(T-01 등)는 저장하지 않고 표시 시점에 정렬 순서로 파생한다.

새 API: `GET /api/issue-tickets` → `status = "open"`인 티켓만 반환(`getOpenIssueTickets()`). 새 모바일 컴포넌트
`IssueTrackingTab.tsx`가 이를 렌더링하며, KPI 선택 칩은 없다(수치 지표가 아니므로).

## 6. 제264회 실측 데이터

7인(이태열·한은진·옥은림·김미영·윤현아·최양희·신수정)의 실제 264회 발언에 대해 사람이 회의록을 직접 검토해
산출한 KPI 값을 `statementInsights`에 직접 시딩한다(AI 파이프라인 재실행이 아님 — 재실행은 신규 공식·신규
지침을 반영한 새 프롬프트로 재추출해야 하는데 그 결과가 이 검증값과 정확히 일치할 보장이 없다). 출처 투명성을
위해 `rubricVersion: "v2.0-5kpi-264-verified-sample"`, `sonnetModel: "manual-verified"`로 표시해 파이프라인
산출물과 구분한다. 정책생산력처럼 정수합/대안수 공식상 반올림 표시값(2.7·2.3)을 정확히 만들 수 없는 경우
공식에 맞는 정밀값(2.67·2.33)을 저장한다 — 화면 표시값이 사람이 말한 수치와 소수점 둘째 자리에서 다를 수
있지만, 저장값과 공식이 항상 일치해야 한다는 원칙을 우선한다.

이슈 티켓 8건(T-01~T-08)도 동일 시딩 스크립트에서 함께 생성한다.

## 6.5 회의 단위 최소 표본 기준 완화 (구현 중 발견된 필수 변경)

264회 실측 데이터를 시딩한 뒤 확인해보니, 최양희 의원의 저도 사업 보조금 질의(실시간압박력·
성과전환력 핵심 사례)가 실제로는 `/api/insights` 목록에 나타나지 않았다. 원인: 그 회의(본회의
제2차, meetingId=3)에서 의사진행 발언만 한 의장·예결위원장을 빼면 실질 발언 의원이 최양희
1명뿐이고(다른 6인은 5분자유발언이라 애초에 수집되지 않음), 기존 `getInsightRows()`의
`MIN_SUBSTANTIVE_MEMBERS_PER_MEETING = 3` 게이트가 이 회의 전체를 결과에서 제외했다.

이 게이트는 v2.0에서 "표본이 너무 작아 회의 단위 비교가 의미 없는 회의를 거른다"는 의도로
3으로 설정됐으나, 실제로는 5분자유발언 정책(수집 금지)과 상호작용해 "실제로는 유의미한 내용이
있지만 참여자 수만 적은" 회의까지 통째로 숨기는 부작용을 낳았다. 논의 후 이 값을 **1로 완화**
(사실상 "실질 발언 의원이 0명인 회의만 제외")하기로 결정했다 — `backend/lib/queries/insights.ts`,
`docs/rubric/CLAUDE.md` §1.1, 루트 `CLAUDE.md`에 반영.

## 7. 검증

백엔드 단위 테스트(`kpi.test.ts`, `extractQaRounds.test.ts`) 기대값 갱신, 타입체크, 마이그레이션 후 컬럼
확인, 시딩 스크립트의 0단계(meetingId/statementId 조회) 결과를 사람이 직접 확인한 후 진행, API curl 검증,
모바일 웹 빌드로 5개 라벨·이슈추적사항 탭·상세화면 태그 렌더링 육안 확인.
